# Control Mapping

This document illustrates how common technical and operational practices can be mapped to ISO/IEC 27001:2022 Annex A controls. The examples are drawn from typical activities in a small software development organization.

The goal is to show the connection between day-to-day security work and the governance framework.

## Mapping Table

| Practice / Control Area                  | Example Implementation                              | Primary ISO 27001:2022 Annex A Controls | Notes / Justification |
|------------------------------------------|-----------------------------------------------------|-----------------------------------------|-----------------------|
| Secure authentication                    | MFA enforced on all user accounts and admin access | A.5.17, A.8.5                          | Protects authentication information and implements secure authentication mechanisms. |
| Configuration management                 | Infrastructure as Code with peer review and drift detection | A.5.8, A.8.9                           | Security addressed in project management; configurations are managed and protected. |
| Secure coding practices                  | Linting, input validation, dependency scanning in CI | A.8.25, A.8.28                         | Secure development lifecycle and secure coding principles applied during development. |
| Logging and monitoring                   | Centralized logs with alerting on security events  | A.8.15, A.8.16                         | Events are logged and monitoring activities are performed. |
| Access reviews                           | Quarterly access certification for production systems | A.5.18                                 | Access rights are reviewed and adjusted on a regular basis. |
| Vulnerability management                 | Regular scans + patching process for OS and applications | A.8.7, A.8.8                           | Protection against malware and management of technical vulnerabilities. |
| Data backup and recovery                 | Automated daily backups with tested restore procedures | A.8.13, A.8.14                         | Information is backed up and processing facilities have redundancy. |
| Supplier security                        | Security questionnaire + contractual clauses       | A.5.19, A.5.20, A.5.22                 | Security requirements defined and monitored in supplier relationships. |
| Incident response                        | Documented process with post-incident reviews      | A.5.24, A.5.26, A.5.27                 | Planning, response, and learning from incidents. |
| Physical and environmental controls (remote) | Clear desk policy for home offices + secure device handling | A.7.7, A.7.9                           | Clear desk and protection of assets off-premises (adapted for remote workforce). |
| Awareness and training                   | Annual security training + phishing simulations    | A.6.3                                  | Personnel receive appropriate security awareness and training. |
| Segregation of duties                    | Code review required before merge to main; separate deploy approvals | A.5.3                                  | Conflicting duties are separated to reduce risk of fraud or error. |

## Cross-Framework Notes (Optional)

- **NIST CSF 2.0** (example mappings):
  - Protect (PR): Many access control and secure configuration items.
  - Detect (DE): Logging and monitoring.
  - Respond (RS): Incident management practices.
  - Recover (RC): Backup and business continuity.

- **BSI IT-Grundschutz** (German context):
  - Several controls align with Grundschutz modules for application security (APP), infrastructure (SYS), and organization (ORG). The 5×5 risk matrix is also commonly used in German public-sector assessments.

These are high-level illustrations only. Formal mapping should be performed against the organization's specific Statement of Applicability.

## How Toolkit Artifacts Can Serve as Evidence

The artifacts generated by this toolkit can support demonstration of control implementation:

- **Risk Register + Heatmap**: Evidence of risk assessment and treatment planning (supports A.5.8, A.5.9, and risk-related requirements in Clause 6).
- **Gap Analysis (Annex A Controls sheet + Summary)**: Shows which controls have been considered and their current implementation status (directly supports the Statement of Applicability and A.5.35).
- **Policies**: Demonstrate that policies exist, are documented, and contain references to the controls they support (A.5.1 and multiple domain-specific controls).
- **Control Mapping (this document)**: Helps connect technical/operational activities to the ISMS framework.

In a real audit or assessment, these would be supplemented with:
- Actual evidence of implementation (screenshots, logs, configuration exports)
- Records of reviews and approvals
- Interviews and walkthroughs

## Limitations

This mapping is illustrative and based on the fictional Aether Labs scope. Every organization must perform its own analysis based on its risk assessment, legal obligations, and chosen controls.

No reference is made to any external portfolio or specific projects outside this toolkit.
